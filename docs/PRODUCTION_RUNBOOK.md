# Production runbook — Render and PostgreSQL

The canonical deployment is Render: one API web service, one worker and one managed PostgreSQL database declared in `render.yaml`.

## Required configuration

- `NODE_ENV=production`
- `DATABASE_URL` from the managed Render PostgreSQL resource
- `JWT_SECRET` generated by Render
- `SEED_PASSWORD` supplied through Render secrets
- `ALLOWED_ORIGINS=https://invexaretail.com,https://www.invexaretail.com`
- `APP_VERSION` set to the deployed commit when available

Never commit secret values or a production database URL.

## Release

1. Merge only after CI passes.
2. Render runs `npm run db:migrate` and `npm run db:verify` in the API pre-deploy step.
3. Start the API and worker from the same reviewed commit.
4. Verify `/health`, `/ready` and `/meta`.
5. Confirm readiness reports database persistence and repository state `ready`.
6. Test authentication and a read-only inventory flow.

Application startup does not create or alter tables. Schema changes must be committed Prisma migrations. Never run `prisma db push --accept-data-loss` against staging or production.

## Backup and recovery

Use the Render-managed PostgreSQL backup/retention mechanism. Before a schema change or data import, take an on-demand backup. Restore into an isolated database first, compare schema and row counts, then run API health, readiness, authentication and read-only smoke tests.

Record source/target identifiers, timestamps, checksum or backup identity, table counts, integrity results, RTO/RPO and reviewer sign-off in the release evidence. See `docs/POSTGRESQL_MIGRATION.md`.
