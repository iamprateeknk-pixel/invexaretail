# Inventory-domain audit (2026-09-25)

Scope: Invexa's inventory *logic* - not the plumbing (that is covered by `docs/guide-status.md`). Method: four inventory-management frameworks (inventory optimisation, replenishment strategy, cycle counting, shelf-life management) were used as the checklist, and every relevant module was read end to end and traced to its callers. Findings were confirmed in code, not assumed. Where a finding was safe and testable it was fixed in this pass, with tests; the rest are ranked backlog with a recommended design.

Severity: **P0** = wrong or unsafe stock/tenant behaviour in normal use · **P1** = wrong recommendation/KPI or a scalability trap · **P2** = capability gap versus a competent inventory SaaS.

## Fixed in this pass

| ID | Finding (evidence) | Fix |
|---|---|---|
| **P0-1** | **Expired stock was allocated first.** `allocateLots`/`allocateFefo` (`lib/warehouse-workflow.ts`) only checked the lot's `status` field. Nothing ever sets a lot to `EXPIRED` when its date passes, and FEFO sorts the *earliest* expiry first - so a lapsed lot still marked AVAILABLE was the first lot handed to customer orders (`lib/orders.ts`, incl. marketplace webhook), job consumption and transfer creation. The only shipped industry pack (grocery: dairy, produce, bakery) has `expiryBlocking: false`. | Allocation is now expiry-date aware (usable *through* the expiry date, expired the day after); a manual override cannot pull a lapsed lot either. Tests in `warehouse-workflow.test.ts`. |
| P0-1b | Five separate "days until expiry" implementations, all on the server's local clock with different rounding (`expiry.ts`, `expiry-board.ts`, `expiry-alerts.ts`, `intelligence-actions.ts`, `dashboard.ts`, `kg-pick.ts`). Between midnight and 05:30 IST a lot expiring "today" looked a day older than the store saw it. | One helper, `lib/expiry-date.ts` (business timezone, date-only expiry never shifted by the host zone), used everywhere. |
| **P0-2** | **Dashboard KPIs were wrong four ways** (`lib/dashboard.ts`): `pendingCounts` was *every* count; `expiredTillDate` counted any item that ever had a lapsed lot even with zero stock; a lot expiring today counted as expired; the "next month" window was about one day wide. | Rewritten: pending = awaiting review; expiry KPIs count only lots that still hold stock; real calendar-month windows. Tests added. |
| **P0-3** | **Multi-tenant identity was global, and Branch was not tenant-scoped.** `Item.code`, `Location.code` and `Branch.code` were unique across *all* companies - the second customer to use a SKU or location code already taken fails. Separately `lib/branch-service.ts` never used `Branch.companyId`: `GET /branches` listed every company's branches and update/archive worked on any company's branch by id. | Migration `20261106090000_company_scoped_codes` (unique per company; additive-safe; `prisma migrate diff` shows no drift). Branch service/routes now company-scoped and stamp the creating company. Real-Postgres tests: `company-scoped-codes.postgres.test.ts`. |
| P1-1 | **Min/max policy was not min/max.** Both intelligence paths recommended ordering *up to target* whenever stock was below **target**, so a healthy item sitting between min and target produced a transfer/purchase every time the screen opened. | One shared planner, `planRuleReplenishment` (`lib/replenishment.ts`): act only at or below min, then order up to target. |
| P1-2 | Stock already dispatched to a store was ignored (`StockLedger.inTransit` is never written), so the same need was re-ordered while a transfer was in flight; and a donor could be drained below its *own* minimum, creating the next stockout elsewhere. | Incoming transfers counted from the Transfer table; donors keep their own reorder minimum (`protectedQty`). |
| P1-3 | `GET /items/:id/forecast` counted open purchase orders as `SUBMITTED/APPROVED/PARTIALLY_RECEIVED` but **not `SENT`** - once a PO was sent to the supplier its quantity vanished from "on order" and the item was re-ordered (the purchase plan handled `SENT`; the forecast did not). | Single `OPEN_PO_STATUSES` constant used by both. |
| P1-4 | `serviceLevelZ` silently returned the **95%** z-score for any service level except 90/95/98/99/99.5 - asking for 97% or 99.9% quietly produced 95% safety stock. | Exact inverse-normal for any level 50-99.99; out-of-range is rejected (400 on the route), not defaulted. |
| P1-5 | ABC ranking **mixed units**: a lot with no cost contributed its unit *count* as if it were rupees (`lib/abc-cycle-count.ts`), so 10,000 cheap uncosted units outranked a costed item worth far more. | With any cost data, value is currency only; uncosted items are held in class B (unknown value is neither top priority nor ignorable); with no costs at all, quantity is used uniformly. |
| P1-6 | **Cycle-count cadence never gated anything.** A/B/C set only a due date on the assignment; eligibility was just "not currently assigned", so every A item was eligible every day. | Plan now knows `lastCountedAt`/`daysSinceCounted`; an item is eligible only when never counted or a full cadence has passed. |
| P1-7 | PO/JOB numbers were `PREFIX-<last 8 digits of Date.now()>` - the suffix repeats every ~27.8 h and the column is globally unique, so a collision fails the create. | `lib/document-number.ts`: date stamp + 6 random characters. |

Also fixed earlier in this engagement (already committed): expired/duplicate marketplace webhook problems, role gates on stock adjustment and import APIs, atomic canonical stock posting on every on-hand path.

## Open findings - inventory optimisation

| ID | Sev | Finding | Recommendation |
|---|---|---|---|
| O-1 | P2 | Reorder rules are **hand-typed min/target only**. `computeSafetyStock` exists but is used solely by the ad-hoc `/forecast` endpoint - it never proposes or checks a rule. | Nightly job: per item-location compute safety stock, reorder point and order-up-to from demand, lead time and a service level; store as *suggested* min/target; a human accepts (same accept/dismiss pattern as the Action Center). **Status: suggestions endpoint `GET /reorder-rules/suggestions` (`reorder-suggestion.ts`); nightly job/accept-dismiss flow not built.** |
| O-2 | P1 | Demand model is thin: no XYZ (demand variability) segmentation; normal-distribution safety stock applied to zero-heavy intermittent demand (needs Croston/SBA or an ADI/CV² switch); population std-dev; first window day is partial; **stockout days count as zero demand** (censored demand understates true demand); `SALES_RETURN` not netted. Demand comes only from `StockMovement` `SALES_DEDUCTION`, which is written by order fulfilment and the staged import - the **legacy** ERP sales import (`/imports/sales/*`) writes `InventoryMovement`/daily rows instead, so stores fed by it may show no demand history. | Classify ABC x XYZ; per-class service levels (guide table: A-X 99% ... C-Z 80%); use Croston for intermittent items; exclude stockout days; net returns; confirm which sales-import path the tenants actually use and unify the demand source.  **Status: Croston/SBA + ADI/CV2 + XYZ + returns netted + stockout days censored + legacy daily sales import unified with order/staged-import sales via `lib/sales-demand.ts` (used by forecast, plan, suggestions, intelligence, inventory health).** |
| O-3 | P1 | Lead time is a static `Supplier.leadTimeDays`, a query parameter, or a default of 7; lead-time **variability is always 0**. `computeVendorScore` already measures actual lead time and on-time % but nothing feeds it back. | Use the supplier's measured mean and std-dev lead time in safety stock; surface "lead time is a default" as low confidence (already partly done).  **Status: partially/fully addressed - measured supplier lead time mean/std feeds safety stock (`po-planning.ts`).** |
| O-4 | P2 | No EOQ, case-pack/MOQ multiples, price breaks or budget constraint in `planPurchases` (MOQ only raises a quantity). `ReorderRule.minQty/targetQty` are `Int`, so **decimal (KG) items cannot have fractional minimums**. | Add order-multiple and EOQ options; make rule quantities `Decimal` with the Decimal migration.  **Status: decimal reorder quantities; `ReorderRule.orderMultiple` case pack; opt-in EOQ (`orderingCost`+`holdingRatePercent`); `budget` cap defers least-urgent lines. Supplier price breaks still open (no data model).** |
| O-5 | P1 | **No valuation or inventory-health metrics**: no turns, days on hand, dead/slow stock, stock ageing, GMROI, fill rate or stockout rate; no costing method (FIFO / weighted average). Cost lives untyped in `Lot.attributes` JSON (`purchaseValue`/`purchaseRate`); `Item` has no cost field; money is `Float`. | Add typed lot cost + a valuation report (weighted-average to start), then the health KPIs. This also makes ABC by *usage value* possible.  **Status: partially/fully addressed - `lib/inventory-health.ts` + `GET /reports/inventory-health` (valuation, turns, ageing, dead/slow). Costing method beyond lot cost/weighted-average, GMROI, fill rate still open.** |
| O-6 | P1 | Position/forecast use **gross on-hand** - lots that are BLOCKED, QUARANTINE or expired still count as cover (`purchase-orders/plan`, `/forecast`). | Compute sellable cover (AVAILABLE, unexpired, minus reserved) via one shared function.  **Status: partially/fully addressed - shared `lib/sellable-stock.ts` used by plan, forecast, intelligence.** |
| O-7 | P1 | `StockLedger.inTransit` is **never written**: source stock is deducted at pick-confirm and the destination is credited at receipt, so stock in between is in no bucket and invisible to network views. (Guide Week 13 asks for explicit in-transit accounting.) | Post to `inTransit` at dispatch and release at receipt; needs the `reserved`/`inTransit` service-command decision noted in `docs/inventory-posting-coverage.md`. **Status: addressed - pick-confirm adds to source-lot `inTransit` (TRANSFER_OUT marked `inTransit`), receipt releases received+damaged+short; older transfers untouched; no network-wide in-transit report yet.** |
| O-8 | P1 | Scalability: the intelligence route loads the **entire `StockLedger` table (all tenants)** per request (`prisma.stockLedger.findMany({ select })` with no `where`), then filters in memory; several list endpoints are unpaginated (`GET /purchase-orders`, orders capped at 200). | Filter by company/location in the query; paginate; add a load test at target volume (Week 19).  **Status: partially/fully addressed - intelligence ledger query company-scoped; `GET /purchase-orders` paginated. Load test still open.** |

## Open findings - replenishment

|---|---|---|---|
| R-1 | P2 | Routing picks a **single** donor (warehouse first, then largest), no cost/lead-time comparison, and hard-codes "purchase into H.O. Basni" as the fallback. ## Open findings - cycle counting

| ID | Sev | Finding | Recommendation |
|---|---|---|---|
| C-1 | P1 | Count tolerance is **recommendation-only and fail-open** (`lib/count-tolerance.ts`): with no `ToleranceRule` configured, only "repeated variance" ever triggers - a 40% variance produces no recommendation. Nothing forces a blind recount by a different user, and nothing auto-accepts a variance inside tolerance, so every count needs a manual review. | Ship a sensible default rule (percent and value); enforce recount above it; auto-approve within tolerance (guide Week 12).  **Status: default tolerance; optional `COUNT_ENFORCE_RECOUNT=true` refuses approving an out-of-tolerance first count (409 RECOUNT_REQUIRED). Enforcing a different user for the recount is not done.** |
| C-2 | P1 | No **triggered counts** (zero balance, negative on-hand, large adjustment, post-receipt discrepancy) - and the ABC plan skips `onHand <= 0` rows, so zero and negative balances are the items that never get counted. | Generate high-priority count tasks from those events.  **Status: negative balance, over-reserved and ZERO_BALANCE-with-recent-sales triggers. Post-receipt discrepancy trigger still open.** |
| C-3 | P1 | No root-cause capture, so variances are adjusted but never analysed. Accuracy KPI is exact-equality per record (not tolerance-based, not value-weighted, not by ABC class); `dashboard.stockAccuracyPercent` also includes unreviewed counts. | Reason codes on review; accuracy = within tolerance, reported by class and by value.  **Status: reasonCode at review + `GET /reports/count-variance-reasons`; `GET /reports/count-accuracy-breakdown` (tolerance-based, value-weighted). Accuracy per ABC class not done.** |
| C-4 | P2 | ABC is by *stock value on hand*, not usage value (annual demand x cost): an overstocked slow mover ranks A. Cadence (7/30/90 days) is a hard-coded constant, not per-tenant. A-weekly is heavy versus the common monthly. | Rank by usage value once O-5 exists; make cadence a setting. |

## Open findings - shelf life

| ID | Sev | Finding | Recommendation |
|---|---|---|---|
| S-1 | P1 | Horizons are fixed **7 / 30 / 90 days** for every product. `Item.shelfLifeDays` is captured and validated but **used nowhere**; lots have no manufacturing date, so remaining-shelf-life % is impossible; there is no sell-by buffer and no customer minimum-RSL requirement in allocation. | Use RSL-% zones (green >67, yellow 33-67, red 10-33) from shelf life; add `manufacturedAt` and a per-customer minimum RSL.  **Status: RSL zones (`shelf-life.ts`), `Lot.manufacturedAt` (migration `20261106160000`, `PATCH /lots/:id/manufactured`), and a per-order-line `minRslPercent` enforced in allocation (`allocateLots`); lots with unknown RSL pass.** |
| S-2 | P1 | No **sell-through vs expiry** projection: the engine never compares days of cover with days to expiry, so it cannot say "you will not sell these 40 units before they expire". Markdown advice is generic (<=7 days), and there is no markdown/donation workflow. | `atRiskQty = onHand - avgDailyDemand x daysToExpiry` per lot; drive markdown, transfer-to-faster-branch, or donate from it.  **Status: partially/fully addressed - sell-through-based `atRiskQty` markdown recommendations.** |
| S-3 | P1 | No worker sweeps lots to EXPIRED/blocked; `expiryBlocking` defaults to **off** for grocery. (The allocator now excludes lapsed lots regardless, but display, transfers and reports still rely on manual blocking.) | Daily sweep + default `expiryBlocking` on for perishable categories.  **Status: partially/fully addressed - `lib/expiry-sweep.ts` worker sweep marks lapsed lots EXPIRED. Default `expiryBlocking` flip still open.** |
| S-4 | P2 | `syncExpiryAlerts` is dead code (never called); alert rows are only created by the write-off route, while the board is computed live. | Either schedule the sync or drop the model. |
