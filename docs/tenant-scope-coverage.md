## Identity - not yet audited with a lint rule

`lib/enterprise-repository.ts` is entirely in-memory (`enhancedUsers` array,
filtered by `companyId` in most read paths like `listUsersByCompany`, but
`findUserById`/`findUserByEmail` do **not** filter by company - a user id or
email is looked up globally, then the caller is expected to check
`user.companyId` itself). This is the same "rely on caller discipline, not
the repository" pattern being retired from Catalog above. Scoping Identity
properly needs its own `TenantContext`-typed repository
(`lib/repositories/user-repository.ts`, not built this week) wrapping
`enhancedUsers`, plus the equivalent for the Prisma-backed `User` model in
database mode. Tracked as a follow-up, not attempted this week to keep this
change reviewable (auth call sites are the highest-blast-radius place to get
a refactor wrong - see ADR-003's own scope discipline).

## Organization (Branch/Location/CompanyProfile) - not yet audited

`lib/saas/tenant-scope.ts`'s `locationOwners`/`itemOwners` maps are exactly
the "in-memory ownership map" pattern this week's task text calls out by
name as insufficient on its own. They remain in place (removing them
outright would break `enforceOperationalCompanyScope`, still a useful
defense-in-depth middleware layer) but are no longer the *only* check for
Catalog - see the scoped repository above. Location/Branch scoping is not
migrated this week; tracked as a follow-up alongside Identity.

## Control-plane elevation

No generic bypass flag exists in `TenantContext` (`lib/tenant-context.ts`) -
only an optional `elevation: { reason, actorId }` field, which nothing
constructs yet. Wiring an actual audited elevation flow through
`lib/saas/control-plane.ts` (support impersonating a tenant, with a reason
and the operator's id recorded) is a follow-up, not implemented this week.

## Compound tenant unique constraints - identified, not yet changed

`Item.code` is globally `@unique` in `prisma/schema.prisma`, not
`@@unique([companyId, code])`. Two different companies cannot use the same
product code today, which is very likely wrong for a multi-tenant catalog.
Not changed this week: `lib/persistence.ts`'s ERP-import upsert path matches
items by `code` alone (`prisma.item.upsert(...)`) and would need the same
compound-key treatment in the same change, and that import path has its own
test coverage that a rushed constraint change could silently invalidate.
Flagged here as a concrete, scoped follow-up rather than attempted
alongside everything else this week.
