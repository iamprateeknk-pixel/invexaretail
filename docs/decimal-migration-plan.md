# Decimal field dictionary and migration plan (Week 5)

Prepares the Float -> Decimal conversion without executing it against
production data yet, per the guide's "prepare a safe, measurable
conversion... without changing stock truth yet." Schema.prisma keeps
`Float` types for now; this document is the frozen dictionary the actual
conversion PR (a future week) implements against.

## Why this matters

`Float` (IEEE 754 double) cannot represent most decimal fractions exactly
(`0.1 + 0.2 !== 0.3` in every language that uses it, JavaScript included).
For stock quantities and money this is not a rounding-error curiosity - it
is the exact class of bug that makes reconciliation reports not add up and
lets tiny drifts compound across millions of postings. Postgres `NUMERIC`
(Prisma `Decimal`) stores the exact decimal value.

## Precision, scale and rounding policy by category

| Category | Decimal type | Rounding policy |
|---|---|---|
| **Money** (prices, costs, totals, value-at-risk/stake thresholds) | `Decimal(14,2)` | Round-half-up to 2dp at the point a value is *finalized* (invoiced, posted); intermediate calculations (e.g. landed-cost allocation across lines) carry full precision and only round the final stored value, never round-then-recompute. |
| **Tax / percentage rate** | `Decimal(6,3)` | Round-half-up to 3dp; GST rates in practice are whole or half percentages (5, 12, 18, 28) but 3dp headroom covers any future blended/composite rate without a second migration. |
| **Quantity** (stock, transfer, count, movement, order-line quantities) | `Decimal(14,3)` | No rounding for PCS (whole-unit) items - enforced at the application layer, not the column, since the same column serves both PCS and KG items (`Item.decimalQuantity` already distinguishes these). KG/decimal items round-half-up to 3dp (gram precision). |
| **Weight / dimension** (packing, shipment) | `Decimal(10,3)` | Round-half-up to 3dp (gram/millimeter precision). |
| Geo coordinates, SLA hours, derived analytics (sales velocity, days of cover) | Stays `Float` | Not stock or money truth - display/estimation values where IEEE 754 precision is irrelevant and Decimal's overhead buys nothing. |

`Decimal(14,2)`/`Decimal(14,3)` give headroom to ₹999,999,999,999.99 /
999,999,999,999.999 units respectively - far beyond any plausible single
row value for this business, so overflow is not a realistic migration risk.

## Calculation-path inventory

24 files perform rounding/formatting arithmetic (`.toFixed(`, `Math.round(`)
on these fields today - `lib/price-guardrails.ts`, `lib/count-tolerance.ts`,
`lib/po-planning.ts`, `lib/weight-allocation.ts`, `lib/lot-allocation.ts`,
`lib/kg-pick.ts`, `lib/qc-gate.ts`, `lib/warehouse-workflow.ts`,
`lib/transfer-packing.ts`, `lib/po-receipt.ts`, `lib/stock-take-campaign.ts`,
`lib/intelligence-actions.ts`, `lib/approval-rules.ts`,
`lib/report-builders.ts`, `lib/dashboard.ts`, `lib/command-center.ts`,
`lib/carrier-adapter.ts`, `routes/core.ts`, `routes/transfer-logistics.ts`,
`routes/command-center.ts`, `routes/catalog-procurement.ts`,
`routes/enterprise-analytics.ts` (plus `lib/request-metrics.ts`, `lib/db.ts`
for unrelated latency-formatting `.toFixed()` calls - not stock/money paths).
Every one of these currently does plain JS `number` arithmetic
(`a + b`, `a * b`, `Math.round`), which works today because the columns are
`Float`/JS `number`. Once a column becomes Prisma `Decimal`, the value
returned to application code is a `Decimal.js`-family object, not a
`number` - `+`/`*`/`Math.round` do not work on it. **Converting the schema
type without converting these call sites in the same change is not a
partial migration, it is a broken one** (every arithmetic expression on a
converted field would throw or silently coerce to `NaN`). This is the
concrete reason the guide's "prepare... without changing stock truth yet"
framing matters: the schema/column change and the ~24-file application
rewrite must ship together, reviewed together, in the actual conversion
week - not staged as "schema first, code later."

## Migration rehearsal (executed, not just planned)

Rehearsed against a disposable local Postgres copy (`retail_decimal_rehearsal`),
seeded via `npm run db:seed` plus hand-inserted rows covering the fraction,
KG-quantity and rounding-boundary cases the guide's fixtures list asks for,
scoped to `StockLedger` (the highest-stakes table) as the representative
slice:

**Before** (row count, aggregate checksum, per-row raw values):
```
row_count | sum_before (Float, SUM aggregation)
        8 | 312.44549989999996        -- note: already visibly imprecise
                                          Float noise, not migration error
```
Per-row values included `12.345`, `0.1`, `0.3`, `1.1`, and a deliberately
injected boundary case `100.0004999`.

**Exception detection** (run *before* altering any column - "do not
silently round historical values"): flag any row where
`ABS(value - ROUND(value::numeric, 3)) > 0.0001` (a tenth of a gram/rupee-
fraction - anything smaller is float representation noise, not real
precision):
```
id                   | column  | original_value | proposed_value | delta
ledger-pathological  | onHand  | 100.0004999     | 100.000        | 0.0004999
```
One row flagged, as designed - this is the exception report entry a real
migration run would route to human review before proceeding (not auto-round
and move on).

**Migration** (executed inside a transaction, rehearsal only - not run
against any real data):
```sql
ALTER TABLE "StockLedger"
  ALTER COLUMN "onHand"    TYPE NUMERIC(14,3) USING ROUND("onHand"::numeric, 3),
  ALTER COLUMN reserved    TYPE NUMERIC(14,3) USING ROUND(reserved::numeric, 3),
  ALTER COLUMN "inTransit" TYPE NUMERIC(14,3) USING ROUND("inTransit"::numeric, 3),
  ALTER COLUMN quarantine  TYPE NUMERIC(14,3) USING ROUND(quarantine::numeric, 3),
  ALTER COLUMN damaged     TYPE NUMERIC(14,3) USING ROUND(damaged::numeric, 3);
```

**After**:
```
row_count | sum_after (NUMERIC, exact)
        8 | 312.445
```

**Reconciliation**: `|312.44549989999996 - 312.445| = 0.0004999`, against a
tolerance of `0.0001 × 8 rows = 0.0008` - within tolerance, and the entire
delta is attributable to the one already-flagged exception row (which the
migration rounded per policy since Decimal columns must hold *some* value;
the flag is what makes that rounding visible and reviewable, not what
prevents it). Row count unchanged (8 -> 8). Column type confirmed
`numeric(14,3)` post-migration.

## Dual-read/dual-write

Not needed. `StockLedger` (and every other table in the dictionary) has
exactly one reader/writer path per row at any time - there is no
long-running background job or external system reading these columns
independently that would need a transition window. The actual conversion
can be a single migration + single deploy (schema change and the ~24-file
application-code change together, per above), not a phased dual-write
rollout. If a future table gains an external consumer (e.g. a BI export
pipeline reading `StockLedger` directly) before this conversion ships,
revisit this section before proceeding.

## Rollback plan

Standard Prisma migration rollback: `ALTER COLUMN ... TYPE DOUBLE PRECISION
USING value::float8` reverses the type change (Postgres `NUMERIC -> FLOAT8`
is always representable, unlike the forward direction). The real risk is
not the column type reverting cleanly - it is that the ~24 files converted
to `Decimal` arithmetic in the same deploy would need to revert
*atomically* with the schema, since (per above) Decimal-typed code cannot
run against Float columns and vice versa. Rollback is therefore "redeploy
the previous commit and run the down-migration," never "revert code but
leave the schema" or the reverse.

## Pilot slice executed: ApprovalRequest.valueAtStake

Per the guide/this plan's own framing - "the schema/column change and the application-code change
must ship together" - the first real, incremental conversion picks the single safest field rather
than the full 80-field/24-file sweep in one change: `ApprovalRequest.valueAtStake` is write-only in
application code (`lib/approval-rules.ts`'s `checkApprovalGate`, one create call) and never read
back into arithmetic or a relational comparison anywhere - the only comparison against a money
field in this flow, `ctx.value >= rule.valueThreshold` in `findTriggeredRule`, compares the
plain-number `value` argument against `ApprovalRule.valueThreshold`, which stays `Float` for now
(deliberately not touched in this slice - see below).

Done: schema (`Decimal @db.Decimal(14,2)`), migration
(`20261108090000_approval_request_value_decimal`, rounds existing rows per the money policy, same
`ROUND(x::numeric, 2)` pattern as the rehearsal above), and the two JSON-response call sites that
needed a code change - `GET /approval-requests` and `POST /approval-requests/:id/decide` in
`routes/operations-extension.ts` now explicitly `Number(...)` the field before responding, since
`Prisma.Decimal`'s default `toJSON()` serializes as a *string*, which would otherwise have silently
changed the API's wire type for every existing consumer (the web app's `CountsPage.jsx` happens to
already wrap the value in `Number(...)`, so it was not actually broken by the old behaviour, but the
API contract itself was still wrong to leave as a silent string). The write path
(`valueAtStake: input.value`) needed no change - Prisma accepts a plain `number` for a `Decimal`
field input and does the conversion itself.

New real-Postgres test, `lib/approval-request-decimal.postgres.test.ts`: a value with 3 decimal
places (`1234.567`) rounds to `1234.57` at the database layer (round-half-up per the policy), and
both routes return it as a JSON `number`, not a string. Not run in this session (no
`TEST_DATABASE_URL`) - run before relying on this in production, per AGENTS.md's required-test
rule for any `prisma/schema.prisma` change.

**Deliberately not touched in this slice**: `ApprovalRule.valueThreshold` (the companion field in
the same feature) - converting it would make `ctx.value >= rule.valueThreshold` compare a `number`
against a `Prisma.Decimal`. JS relational operators (`>=`, `<=`) happen to still produce the right
answer here (they coerce via `valueOf()`/`toString()` to a comparable primitive), but this is exactly
the fragile, easy-to-get-wrong territory the "24-file arithmetic rewrite" risk in this plan warns
about for *any* field that participates in a computation rather than pure storage - not a safe thing
to leave to happenstance JS coercion semantics even where it currently works. `Float` for now.

This is slice 1 of the eventual 80-field migration - the remaining 79 fields (and in particular
the ~24 files performing real arithmetic, not just storage/comparison) still need their own slices,
each with the same discipline: real-Postgres verification before merge, and any comparison or
arithmetic call site converted in the same change as its schema type.

## Slice 4: rule thresholds (`ApprovalRule`/`EvidenceRule`/`ToleranceRule.valueThreshold`)

Decimal(14,2) by migration `20261117090000_rule_thresholds_decimal` (round-half-up to 2dp; the
exception-detection query is in the migration header). This closes the comparison concern the
slice-1 note raised: the rows are converted to plain numbers at the loading boundary
(`lib/decimal-json.ts` `thresholdsAsNumbers`, used in `checkApprovalGate`, the tolerance and
evidence gates) so `value >= threshold` never compares a number with a `Prisma.Decimal`, and every
rule route returns JSON numbers, not Decimal strings. Proven in
`src/routes/operations-extension-rules.postgres.test.ts` (2dp rounding, number on the wire).

The same slice fixed a tenant-isolation gap found while tracing these loaders: the approval/
tolerance/evidence rule lists and QC template list returned every company's rows, their PATCH
handlers updated by bare id, and `checkApprovalGate` applied *any* company's approval rule to the
caller's action. Lists and loaders now filter by the creator's company, PATCH resolves a foreign id as
404, and `checkApprovalGate` requires a `companyId`. The same test file proves it (it fails on the
previous route code).

The QC subsystem had the same shape and is fixed too: every QC template lookup (receiving, transfer
receive, returns, the PO scorecard) and every QC inspection list now filters by the creating user's
company, and the default checklist is created per company (`default-qc-template:<companyId>`) instead
of one shared fixed id. Before this, one company's active QC template made QC mandatory for every
other company's receipts.

## Exception-record policy

Any row flagged during the real (non-rehearsal) migration run is copied to
an `docs/release-evidence/<release>/decimal-migration-exceptions.csv` file
(per the Week 1 evidence-pack convention) with its id, table, column,
original value, proposed value and delta, and is **excluded from the
automatic rounding** - it is fixed by a human decision (which historical
value is correct) before the migration is allowed to proceed on that row.
This rehearsal used an automatic tolerance purely to produce a concrete,
reviewable number for this document; the real migration's exception rows
block completion until resolved, they are not merely logged and rounded
anyway.
